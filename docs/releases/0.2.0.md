# t4a-cuda-kernels 0.2.0

0.2.0 exists because the C ABI revision moved, not because a Rust API changed: `T4A_CUDA_ABI_REVISION` is 14, and a
kernel catalogue pinned at 13 cannot be swapped for this one at runtime. A minor bump is what tells a downstream
`=0.1.2` pin that it has to look, so the number identifies the contract rather than the code (the 0.1.2 note explains
why that distinction was not being kept).

## What changed since 0.1.2

- **`T4A_CUDA_ABI_REVISION` is 14** (`cuda/include/t4a/abi.cuh`, documented in `docs/abi/c-kernel-abi.md`).
- **`reduce` combines the load-ahead with the split pass-1 blocks** (`cuda/src/reduce.cu`): pass 1 of a full-array
  reduction now runs `block = (128, 1, 1)` over `ceil(cubes / 4)` blocks when `plane_width == 32 && cubes <= 8192`.
  The pass-1 partials are bit-identical to revision 13's golden (`tests/data/reduce-golden.tsv`, 1332 cells).
  **The finals are not bit-identical in 48 of those cells**: they differ from the golden only in the payload bits of
  a NaN, never in a value, a sign or the presence of NaN. Those 48 cases are listed in
  `tests/data/reduce-golden-nan-payload.tsv`, and `tests/gpu_reduce_golden.rs` requires the list to stay exactly
  that set — a listed case that becomes identical fails the test, as does an unlisted payload difference — so no
  new NaN and no changed non-NaN value goes unnoticed.

## What a consumer has to do

- A binary that links the kernels by ABI revision must rebuild; the revision check is what makes a stale pair refuse
  instead of producing wrong numbers.
- Nothing in the Rust surface changed: the same entry points, the same types, the same feature names.

## Verification

The evidence of the run that produced this version is in `docs/worklogs/evidence/2026-11-10-pass1-multiwarp/`
(measured on an A100 80GB, driver 580.178.04, CUDA 12.6). The ABI revision is checked against the Rust side in
`tests/planning.rs`; `tests/gpu_reduce_golden.rs` is the numerical golden comparison, and it does not look at the
revision number.
